# FPGA 动态可重配技术调研（动态部分重配置 / Dynamic Partial Reconfiguration）

- 调研日期：2026-09-28
- 范围：概念与术语、各厂商方案（AMD/Xilinx DFX、Intel/Altera PR、Lattice、国产）、实现流程与关键技术点、运行时通道、验证方法、工程实践与典型案例、开源/学术框架、参考资料

## 1. TL;DR

- 动态可重配（业界主流叫法：AMD/Xilinx 的 **DFX**，前称 Partial Reconfiguration/PR；Intel/Altera 的 **Partial Reconfiguration**）指 FPGA 在**其余逻辑持续运行**的情况下，通过加载**部分比特流**只替换器件内某一区域的逻辑。
- 技术上由四件事支撑：**静态区/重配区划分（static region + RP/RM）**、**边界解耦（decoupling/partition pins）**、**物理约束（pblock floorplanning）**、**运行时配置通道（ICAP/PCAP + 主机或片上控制器）**。
- 成熟度：AMD Vivado 的 DFX 流程最成熟、资料最全（UG909 用户指南 + UG947 教程 + DFX Controller/Decoupler IP）；Intel Quartus Pro 有完整的 partition/persona 流程；Lattice 与国产厂商的公开资料少、无成熟公开流程，选型前需向 FAE 确认。
- 主要代价：**工程复杂度显著上升**（floorplanning、每个 RM 单独实现、多套时序签核、验证矩阵膨胀），**重配瞬间业务必须隔离**（decoupler + reset 策略），因此适合"接口稳定、内核多变"的场景：SDR 波形切换、AI 加速核换型、网络协议处理热更新、太空/高可靠场景的修复与余度管理。
- 建议路线：若只是想"更新逻辑"，优先考虑整片重配（remote update）或 FPGA Manager 整片加载；只有当**停机时间不可接受**或**片上需共存多套互斥功能**时才上 DFX，并按本文第 6 节的 checklist 走。

## 2. 概念与术语

| 术语 | 含义 |
|---|---|
| PR / DFX | Partial Reconfiguration → AMD 改名 **Dynamic Function eXchange**，同一技术 |
| Static Region | 静态区：重配期间与重配之后保持不变、持续运行的逻辑（含配置通道、总线互连） |
| RP（Reconfigurable Partition） | 重配分区：器件上可被运行时替换的物理区域，对应 RTL 中一个层次化实例 |
| RM（Reconfigurable Module） | 重配模块：某个 RP 可装载的一组实现；一个 RP 可有多个 RM |
| Configuration | 一种"静态区 + 每个 RP 各选一个 RM"的完整组合；每个配置出 1 个全比特流 + N 个部分比特流 |
| Partition Pins | 静态区与 RP 边界上的"虚拟 IO"，Vivado 在 pblock 范围内自动创建；所有 RM 的端口必须是这些 pin 的**超集** |
| Decoupling / Blanking | 重配加载期间把 RP 与静态区隔离：AXI 侧用 DFX Decoupler（把静态侧 AXI 驱动到恒定值），RP 内部用 shutdown/复位逻辑冻结 |
| ICAP | Internal Configuration Access Port（7 系 ICAPE3 等）：PL 内部的配置写入口，**只能配置已启动的 FPGA**，是运行时部分重配的首选通道 |
| PCAP | Processor Configuration Access Port：Zynq UltraScale+ 由 PS 侧 DevC 模块经 PCAP 写 PL，64-bit 宽 |
| SelectMAP / JTAG / MCAP | 其他配置通道：SelectMAP 是并行从模式口；MCAP 是 PCIe 侧入口（常用于 Alveo 卡经主机重配） |
| Clearing/Blanking bitstream | 先下发"清空"部分比特流把 RP 恢复到空白帧，再加载新 RM，避免新旧帧内容混淆（见 AMD AR 63419 的比特流分类） |

关键机理：FPGA 配置存储器按**帧（frame）**组织，部分比特流就是**只覆盖 RP 所在帧**的比特流；DFX 工具链的核心工作是保证任意 RM 布线后，帧边界、partition pin、静态区路由完全一致，从而使"任一 RM 的部分比特流 + 同一基础全比特流"可自由组合。

## 3. 各厂商方案对比

| 厂商/工具链 | 技术名 | 流程要点 | 运行时通道 | 成熟度/资料 |
|---|---|---|---|---|
| AMD/Xilinx（Vivado） | DFX | static/RP 划分 → 每个 RM 综合 → 逐配置实现 → pr_verify → 全+部分比特流；支持嵌套 RP、Abstract Shell 团队协作流 | ICAP（AXI-HWICAP / DFX Controller IP）、PCAP（ZynqMP DevC）、MCAP（PCIe）、JTAG | 最成熟；UG909 + UG947 + 官方 IP + 大量教程 |
| Intel/Altera（Quartus Pro） | Partial Reconfiguration | 设计分区（Design Partition）→ floorplan PR region → base revision 快照 → 逐 persona 实现 → 部分比特流（.pmsf/.rbp 等）；支持分层 PR（hierarchical PR） | PR IP（Avalon-MM 主机逻辑触发）、PCIe 主机、JTAG；Agilex/Stratix 10 SoC 走 HPS | 成熟；Quartus Pro 专属（Standard 版不支持），OFS 生态可参考 intel/fpga-partial-reconfig |
| Lattice | — | Diamond/Radiant 无等同 Vivado DFX 的公开成熟流程；开源工具链（nextpnr/IceStorm/prjxray）**尚不支持** PR 流 | — | 公开支持差；需要 PR 时基本排除 |
| 国产（紫光同创、安路、高云、复旦微等） | — | 公开文档中**普遍未见**完整的动态部分重配流程；AGM 宣称其 MCU+FPGA 支持比特流在线动态重配 | — | 资料少、结论易过时，选型时必须向 FAE 索要 PDS/TD 中的 PR 章节与例程确认 |
| 开源工具链（F4PGA/prjxray、nextpnr） | — | prjxray 目标是逆向 Xilinx 7 系比特流格式；PR 相关能力仍属实验性，无生产级流程 | — | 学术/研究用途 |

> 注意一个常见混淆：Vivado 文档体系里 **UG909 = DFX 用户指南，UG947 = DFX 教程（tutorial）**，ILA 调试是另一本（UG948/UG908 系），别按 UG947 找"用户指南"。

## 4. AMD/Xilinx DFX 流程（主流路线，展开讲）

### 4.1 设计划分

1. 顶层把可变功能收敛到一个（或几个）层次化实例 `rp1` 下，实例端口即未来所有 RM 的**公共超集**——先定接口，再写 RM。
2. 接口建议全部走 **AXI4/AXI4-Lite/AXI-Stream** 等标准协议，天然匹配 DFX Decoupler 与 DFX Controller 的 shutdown 握手。
3. 静态区包含：时钟（MMCM/BUFG 必须放静态区）、复位、互连（AXI SmartConnect/Network）、配置通道（ICAP/DFX Controller）、调试（ILA）。

### 4.2 Vivado 实现流程（非工程模式骨架）

```tcl
# —— 骨架示例：非工程模式逐 RM 流（命令名以目标版本 UG909/UG947 为准，本机未验证）——
# 1) 综合：顶层（RP 实例为黑盒/桩）+ 每个 RM 各综合一次
read_verilog {top.v static.v}
read_verilog rp1_stub.v                 ;# RP 桩，只含端口声明
synth_design -top top -part <part>
write_checkpoint -force static_synth.dcp

read_verilog rm1.v; synth_design -top rm1 -mode out_of_context -part <part>
write_checkpoint -force rm1_synth.dcp   ;# 同理 rm2、rm3...

# 2) 约束：pblock 定义 RP 物理区域（也可在 XDC 里写）
open_checkpoint static_synth.dcp
create_pblock pblock_rp1
add_cells_to_pblock [get_pblocks pblock_rp1] [get_cells {inst_rp1}]
resize_pblock [get_pblocks pblock_rp1] -add {CLOCKREGION_X1Y2:CLOCKREGION_X1Y3}
set_property GRID_SLR_CROSSING {none} [get_pblocks pblock_rp1]  ;# 视需要禁止跨 SLR

# 3) 逐配置实现：把 RM 网表填进 RP 单元再布局布线
foreach rm {rm1 rm2 rm3} {
    open_checkpoint static_synth.dcp
    read_checkpoint -cell inst_rp1 ${rm}_synth.dcp
    source constraints_static.xdc ; source constraints_rp1.xdc
    opt_design; place_design; phys_opt_design; route_design
    write_checkpoint -force impl_${rm}.dcp
    # 4) 部分比特流；父配置（第一个）同时写全比特流
    write_bitstream -force bit_${rm}.bit
}
# 5) 一致性校验：比较各配置的静态区与 partition pins 是否一致
pr_verify -file impl_rm1.dcp impl_rm2.dcp
```

工程模式下对应 `create_pr_configuration`/`set_property CONFIG.<RP> <RM>` 的项目配置流，GUI 里是 "Create Configuration" 对话框；团队分工用 **Abstract Shell**（静态区交付编译后的抽象 DCP，RM 设计者拿 stub 开发，互不泄露、互不阻塞）。

### 4.3 关键约束与易错点（来自 UG909/社区实践）

- **端口超集原则**：RP 的所有 RM 必须使用同一组 partition pins；RM 之间端口不一致 = 各自都要重做静态区，违背 DFX 初衷。未用的 pin 也要在端口里保留。
- **pblock 形状**：优先**完整时钟区域（clock region）对齐**的矩形；7 系还需注意整列（clock region column）对齐，避免部分帧跨界导致区域不可用或浪费。跨 SLR 的 RP 在 SSI 器件上要显式管理（建议禁止跨 SLR）。
- **partition pin 落位**：大量高速总线穿越边界时，pin 位置不当会拥塞/时序差；必要时手工约束 pin 位置（`set_property PACKAGE_PIN` 不适用，这里是对 partition pin 的 placement 约束）。
- **时钟与复位**：全局时钟一律出自静态区；RP 内只消费时钟，不得在 RP 内生成供静态区用的时钟。RP 内复位要能被 shutdown 信号强制拉住。
- **静态区锁定**：批量出 RM 时用 `lock_design -level routing` 锁静态区布线，保证所有部分比特流与同一静态区兼容。
- **比特流安全**：部分比特流与全比特流的加密/认证要一致管理；先下发 clearing/blanking 比特流再装新 RM 是稳妥做法。

### 4.4 运行时重配通道

| 通道 | 位置 | 典型用法 |
|---|---|---|
| **ICAP（ICAPE3）+ AXI-HWICAP** | PL 内 | 软核 MicroBlaze 或 PS 经 AXI 写 ICAP；最通用的自研方案 |
| **DFX Controller IP** | PL 内 | 官方 IP：从内存（DDR 等）按地址表取部分比特流灌 ICAP，自带 `dfx_axi_shutdown_m` 输出联动解耦；PS 只需 AXI-Lite 写几个寄存器触发换 RM |
| **DFX Decoupler IP** | RP 边界 | 每个 RP 一个；shutdown 有效时把静态侧 AXI 驱动到恒定值、隔离 RP |
| **PCAP（ZynqMP DevC）** | PS | Linux 下 `zynqmp-fpga`（FPGA Manager 框架）走 PCAP；**注意：mainline 的 zynqmp-fpga 长期缺部分重配支持**，实际做法是 Xilinx 内核树补丁或自写 fpga-mgr 后端，或干脆改走 ICAP/DFX Controller |
| **MCAP（PCIe）** | 卡上 | Alveo/加速卡经主机 PCIe 触发重配；Vitis/XRT 里体现为 xclbin 换载（对用户透明的 DFX） |
| **JTAG** | 外部 | 仅开发调试 |

重配时间估算：`T ≈ 部分比特流大小 ÷ 配置端口带宽`。ICAP 32-bit@100 MHz 约 400 MB/s，PCAP 64-bit 约 800 MB/s 量级（依器件而异）。例如 8 MB 部分比特流经 ICAP 约 20 ms 量级；这决定了"换核"不是微秒级操作，调度设计要把这个窗口考虑进去。

### 4.5 验证

- **仿真**：PR 的"加载动作"本身不可仿真；做法是把静态网表 + 某 RM 的 RTL/网表拼在一起做常规仿真（UG909 Simulation 章节），覆盖协议断言与复位/解耦时序。
- **sim_pr_verify / pr_verify**：`pr_verify` 比较两个配置的静态区与 partition pins 是否完全一致（发布前对全部配置两两/对基准跑一遍）；`sim_pr_verify` 是仿真库侧的对应校验。
- **时序**：每个配置（每个 RM）都要独立出时序报告并签核——静态区时序相同，但 RP 内时序随 RM 不同。
- **上板**：先全比特流启动 → 触发 DFX Controller/PCAP 换 RM → 观测解耦期间静态侧业务（如 AXI 流量、计数器）不受扰 → 回读 ID/版本寄存器确认 RM 生效。建议 RM 里放版本寄存器。

## 5. Intel/Altera PR 流程（要点）

Quartus **Pro Edition** 专属流程，核心概念从"RM/Configuration"换成"**Design Partition + Persona**"：

1. 顶层为可变逻辑预留分区实例，静态侧接口用 PR 抖动/握手处理；
2. **Create Design Partitions** 并把分区标记为 PR（root partition + persona 分区）；
3. **Floorplan**：Floorplan Editor 里划定 PR region（分配资源、预留边界）；
4. 编译 **base revision** 得到静态区快照（root partition）；
5. 为每个 persona 建 PR revision，基于快照编译，只重实现该分区；
6. 生成部分比特流（.pmsf → 转开发板可用的 .rbp/.rbf 等），运行时经 **PR IP**（Avalon-MM 触发）或 PCIe 主机加载。

与 AMD 流程同构的坑也存在：persona 接口必须一致、PR region floorplan 决定成败、逐 persona 时序签核、加密时 persona 与静态区需同一密钥（除非启用 multi-authority）。分层 PR（PR region 里再嵌 PR region）两家都支持。官方教程与脚本见 GitHub `intel/fpga-partial-reconfig`（含 Stratix 10 LED persona 入门例）。

## 6. 工程实践与 Checklist

### 6.1 何时用动态重配（决策表）

| 需求 | 建议方案 |
|---|---|
| 只是现场升级固件，允许秒级停机 | 整片重配（remote update / FPGA Manager 全比特流） |
| 片上功能互斥且停机不可接受（如雷达波形切换、协议热切换） | DFX |
| 同一加速接口要跑多种算子/模型 | DFX（加速核换型）——或评估"做大核+参数化"是否够用 |
| 出货量大、想省器件成本（一机多用） | DFX |
| 高可靠/太空：在轨修复、抗 SEU | DFX + 帧回读校验 + SEM/scrubbing |

### 6.2 设计 Checklist

- [ ] RM 接口先冻结：端口集合、位宽、协议（推荐全 AXI）、时钟/复位清单，形成《RM 接口规范》文档
- [ ] 每个 RP 一个 DFX Decoupler；解耦默认值明确（AXI 侧 static 通道给合法恒定值，避免下游协议违例）
- [ ] RP 内所有状态可被 shutdown 信号复位；跨 RP 与静态区的握手（valid/ready）在解耦期间冻结
- [ ] pblock 对齐完整时钟区域、避免跨 SLR；对 pin 拥塞敏感的总线手工放 partition pins
- [ ] RM 内不放 MMCM/PLL/BUFG 生成供外部的时钟；不留调试核在 RM 内（ILA 放静态区经 partition pins 观察）
- [ ] 每个 RM 独立时序签核 + `pr_verify` 全配置比对，纳入 CI
- [ ] 比特流管理：全/部分/清空三类分开版本化，头部带器件 ID + RM 版本；下发顺序 = 清空 → 部分 → 解除解耦
- [ ] 上位机/片上控制器流程含超时与回滚（加载失败回退到已知好 RM）
- [ ] 版本寄存器放每个 RM 固定地址，供运行时确认装载结果

### 6.3 典型应用案例

- **SDR/无线电**：同一射频前端平台按波形（调制解调、信道化）热切换 RM；GNU Radio RFNoC 也有经部分比特流换处理块的实践（GRCon20 报告）。
- **AI 加速**：同一 PCIe 卡在不同负载下换 DPU/卷积加速核；Vitis/XRT 的 xclbin 换载即厂商封装好的 DFX/整片重配混合方案。
- **网络/协议处理**：网卡/网关按流量特征换解析器、过滤器；配 DFX Controller 可由软件毫秒级切换。
- **高可靠/航天**：Xilinx V5QV 等抗辐照器件 + 帧回读 + scrubbing，局部损坏经部分重配修复；SEM IP 管理错误纠正。
- **金融低延迟（与本工作区相关）**：tick-to-trade 路径上"交易所协议解析器/策略核热切换"是 DFX 的合理场景——但要注意解耦 mux 会进关键路径，需评估其对端到端延迟的影响；若只在停盘/维护窗口换逻辑，整片重配更简单。

### 6.4 开源与学术框架

- **FRED**（Scuola Superiore Sant'Anna）：Zynq SoC 上基于 DPR 的加速器运行时，虚拟化 FPGA fabric、支持抢占式重配与实时调度；配套 **DART** 工具自动完成分区/floorplan/比特流全流程（Zynq-7000 与 UltraScale+）。研究与快速原型首选。
- **ZyPR**（2023, ACM TRETS）：端到端构建工具 + 运行时管理器，ICAP 通道。
- **prjxray / F4PGA / nextpnr**：开源比特流逆向与布线，PR 能力仍实验性，适合研究比特流格式而非生产。
- 综述：*FPGA Dynamic and Partial Reconfiguration: A Survey*（ACM Computing Surveys, 2018）——floorplanning、调度、安全各章仍是最好的入门材料；floorplanning 自动化可看 Rabozzi et al. 2017。
