## 0. 结论先行

1. **方法学没有争议，权威内容只有一处**：AMD 官方 UG949 第 6 章 "Design Closure"（它是已下线的 UG1292 的现行载体）+ UG903/904/906/901。社区、博客、中文资料里的所有技巧，几乎都能在这几份文档里找到出处。
2. **开源世界没有"时序修复工具"，只有三样东西值得拿**：① 官方 Tcl Store 的 `designutils`/`junit`/`customqorflows` 应用（可直接用的归因报告与 CI 门禁）；② `analogdevicesinc/hdl` 里那份可直接照抄的 CI 时序门禁 Tcl；③ `Xilinx/RapidWright`——唯一能在 Vivado 之外做时序分析的引擎。**没有找到有实际采用度的独立"时序报告解析器"**，解析逻辑都内嵌在更大的工具里。
3. **最值钱的一条开源算法洞察**：VTR/VPR 和 nextpnr 的时序驱动布局都是**按 slack 归一化的 criticality 加权网络**。这从机制上解释了 Vivado 里那条人人都在背、却说不清理由的规则——**寄存器复制/扇出优化只对失败路径有意义**；余量充足的网权重接近 0，动它纯属浪费。
4. **最容易踩的坑是约束，不是布局布线**：multicycle 只写 setup 会把 hold 检查拖后 N−1 个周期（这是标准 SDC 语义，OpenSTA 源码可证）；`set_clock_groups` 优先级高于 `set_max_delay`（会静默吃掉后者）；TNS/THS 为 0 只表示"没有违例"、不含余量信息（另注意 OpenSTA 一类工具会把 WNS 截断在 0，口径与 Vivado 不同）。**任何优化动作之前先做约束体检。**
5. 落地成果：已把上述内容固化成 skill（SKILL.md + 5 份 reference + 2 个可运行脚本），并**在本机完成脚本自检**（离线解析器有夹具回归；Tcl 脚本用桩函数在 tclsh 下跑通，因为本机没有 Vivado）。

## 2. 官方方法学：十条最该记住的

| # | 结论 | 出处 |
|---|---|---|
| 1 | **签核口径**：WNS>0 且 TNS=0；WHS>0 且 THS=0；WPWS>0 且 TPWS=0 | UG949 Ch.6 |
| 2 | **约束体检的修复顺序**：无时钟/未约束端点 → 生成时钟 → 组合环/latch 环 → 缺 I/O delay → 多时钟 | UG949 Ch.6 |
| 3 | **baselining**：从无用户约束的综合后 checkpoint 开始，先只定义"所有时钟 + CDC"，**先不约束 I/O**（未约束时 I/O 默认被忽略），逐阶段记录 WNS | UG949 Ch.6 |
| 4 | **根因阈值**：逻辑延迟占比 7 系 >25% / UltraScale >50% ⇒ 逻辑主导；布线延迟占比 7 系 >75% / US >50% ⇒ 布线主导 | UG906 |
| 5 | **时钟偏斜目标**：域内 <300 ps、平衡同步时钟之间 <500 ps；无公共节点时可达数 ns，"时序收敛几乎不可能" | UG949 |
| 6 | **控制集**：<7.5% 可接受、7.5~15% 建议降、>15% 必须降；`report_control_sets -verbose`；不要在控制信号上加 MAX_FANOUT | UG949 |
| 7 | **专用块路径**：BRAM 时钟到输出无输出寄存器 ≈1.5 ns、有则 ≈0.4 ns；进出 DSP/BRAM 的路径要流水，**布局前这些路径 setup 余量至少留 500 ps** | UG949 |
| 8 | **先网表后 directive**："在综合或 opt_design 之后识别并改进最长路径，对时序和功耗 QoR 影响最大，且通常大幅减少布局布线迭代次数" | UG949 |
| 9 | **过约束上限 0.5 ns**，且必须"布局后、布线前复位"；`set_clock_uncertainty -from/-to` 是推荐手段（不改变时钟关系、可精确复位） | UG949 |
| 10 | **RQS 是官方捷径**：`report_qor_suggestions` → `write_qor_suggestions` → `read_qor_suggestions`（必须在 opt_design 前）→ 四个阶段都用 `-directive RQS`；ML 策略建议仅 UltraScale+，且各阶段 directive 必须统一不能混用 | UG906/UG904 |

**反模式清单**（官方明确警告）：false path 掩盖真实路径；`set_false_path -through` 不加 `-from/-to`；`all_registers` 这类超大对象列表；只写 multicycle setup；对 I/O 用 max_delay 代替 input/output delay；全局 MAX_FANOUT / DONT_TOUCH / KEEP_HIERARCHY；`CLOCK_DEDICATED_ROUTE=FALSE` 用于量产；布线前猛修 hold；用 `-no_timing_driven`/`Quick`/`RuntimeOptimized` 期待收敛；带 pblock 扫 directive；floorplan 增量 run；waive TIMING-9/10。

### 3.5 开源 EDA 算法（可迁移洞察）

| 项目 | 迁移到 Vivado 的洞察 |
|---|---|
| **VTR/VPR** ★A（代码级） | 时序驱动布局的核心是**按 slack 归一化的 criticality 加权**：`crit = 1 - slack/max_required`，再取幂锐化（默认指数 1~8），作为网络权重的乘数。**这解释了 Vivado 那条规则的机制**：扇出优化/复制只对失败路径有意义。VPR 还用 criticality 直方图（10 桶）判断"是长尾还是聚集"——聚集 ⇒ 试 directive；弥散 ⇒ 必须改 RTL |
| **nextpnr** ★A（代码级） | `weight *= (1 + 10*crit²)`；另有专门的时序驱动详细布局 pass（对关键路径邻域 BFS，给每条网络分配 `net_delay + (slack − domain_slack)/10` 的延迟预算，只接受受影响弧都在 1.1× 预算内的移动）。**它的 Fmax 与 Vivado 不可比**：网络延迟是 RC/pip 类近似、时钟是理想的（无插入延迟无偏斜）、无 OCV/derating、每弧只有一对 min/max 表。当作"布局质量的相对指示"，等同 Vivado 综合后的 `report_timing` |
| **OpenSTA** ★A（代码级） | **SDC 语义的参考实现**。multicycle 的 hold 位移 `(setup_mult−1)·T − hold_mult·T` 在 `search/PathEnd.cc` 有实现——**"N−1 规则"是标准 SDC 语义，不是 Vivado 怪癖**。`report_wns` 文档明写"最差 slack 为正时报告 0"，是 WNS 被截断的证据。`report_checks -group_path_count/-endpoint_path_count/-unique_paths_to_endpoint` 是路径枚举的内存控制手段，对应 `report_timing -max_paths` |
| **OpenROAD** ★A | `repair_timing` 的 setup 修复顺序 `unbuffer → vt_swap → sizeup → swap → buffer → clone → split` 是 `phys_opt_design` 各变换的"罗塞塔石碑"：**clone = 门复制（≈寄存器复制）**，split = 把非关键负载分离到 buffer 后。`gpl -virtual_cts`（布局期建虚拟时钟树建模偏斜）对应 `phys_opt_design -clock_opt` |
| **ABC** ★A | 6 种重定时算法（`retime -M 4/6 -D <ps>` 做延迟目标优化）。这是"逻辑域重定时"的开源对应物；**布局感知的物理重定时**（Vivado `-retime`/`-interconnect_retime`）因为需要物理数据库，开源流程里没有 |
| **AMF-Placer 2.0** ★A | UltraScale 时序驱动解析布局，CPD 比 Vivado 2020.2 差 2.2%。它自陈的缺口——**缺精确器件时序模型、缺设计层级、缺布线反馈**——正是"学术 FPGA 时序数字不能与 Vivado 布线后数字直接比较"的原因清单 |
| `DREAMPlaceFPGA`、`Xplace`、`RippleFPGA`、`OpenPARF` ★A | DREAMPlaceFPGA：criticality 进入 LUT/FF **聚类评分**（对应 Vivado 里打包/控制集决策本身就是时序决策）；Xplace：GPU 加速时序分析使逐迭代时序驱动布局可行；RippleFPGA：UltraScale 上**时钟感知**的同时打包+布局；**OpenPARF 明确不做时序**（目标是有线长与 SLL 数）——提醒"多数 FPGA 学术布局是可布线性驱动而非时序驱动" |
| Tatum（VTR 的 STA 引擎）★A | 支持 setup/hold、时钟偏斜、多时钟、时序例外，可作为"嵌入式 STA 核心"参考。VPR 每个布线迭代打印 `CPD/sTNS/sWNS/hTNS/hWNS`，与 Vivado 同一套指标的非商业出处 |

## 4. 社区经验的精华与冲突

### 4.1 值得吸收的

- **读报告只问四个问题**：逻辑延迟占比？逻辑级数？扇出？时钟偏斜？——四个答案对应四类完全不同的手段。`levels` 大 → 拆多拍；`fanout` 大 → 复制/局部化。
- **hold 有完全不同的打法**：正偏斜利 setup 害 hold；修 hold 要**增加**数据路径延迟。布线前只处理 >0.5 ns 的；布线后仍有则用定点重布三步法：`route_design -unroute -pins <终点输入脚>` → `-auto_delay` → 必要时 `-min_delay <ps>`（含具体计算示例：net 延迟 0.110 ns、hold slack −0.001 ns ⇒ 至少 `-min_delay 111`）。
- **多轮迭代循环**（社区版 `runPPO`）：循环 `place_design -post_place_opt` / `phys_opt_design -directive AggressiveExplore` / `route_design -directive Explore`，用 `[get_property SLACK [get_timing_paths]] >= 0` 提前退出。注意工程里 Post-place/Post-route Phys Opt **默认是关闭的**。
- **不要跳过 Synthesis 报告**：Vivado 综合是时序驱动的，综合后时序报告可信（与 ISE 不同）；跳过它会让问题在顶层集成时集中爆发。
- **高扇出 reset 是重灾区**：Xilinx 员工在论坛的答复就是"duplicate your reset register"；工程做法是每个大模块用自己经过打拍的 reset 版本。
- **脉冲跨时钟域必须先展宽成电平**再同步，同步后再恢复成脉冲（单周期脉冲直接打两拍会漏采）。
- **综合后出现的 hold 违例不要急着改代码**，多数会被布线器自动修掉——但**不能当规则**，会漏掉真正的跨时钟域 hold 问题。

### 4.2 明确冲突、引用需谨慎的

| 社区说法 | 冲突/风险 |
|---|---|
| 优先 `set_clock_groups -asynchronous`，别用 `set_false_path` | clock groups 优先级**高于** `set_max_delay`，会静默吃掉你精心写的 max_delay 路径；Xilinx 员工在论坛给出的唯一解是"改用 set_false_path"——**两条社区建议互相矛盾** |
| `set_false_path` 对同步器路径是常见做法 | 与"false path 永远不是最好答案"直接冲突；通配符极易过度应用 |
| 给每个模块输出都加寄存器 | 会浪费资源、**加剧拥塞反而更差**；反方主张"先删掉路径上所有寄存器再重新切分流水线" |
| LUT+NET ≈ 0.5 ns、levels ≤ 8（7 系 -2 @250 MHz） | UG949 没有这些数字，是经验法则，跨器件/速度等级不通用 |
| `CLOCK_BUFFER_TYPE BUFG` 给高扇出普通网络 | 中文社区偏方：占用稀缺 BUFG、可能引入偏斜 |
| 每阶段 WNS > −300 ps 即可放行 | 来自 Xilinx 公开课（Baseline 方法学），非 UG949 条文，阈值不通用 |
| AXI 的 xREADY 必须寄存 | 与 AMD 自家大量 AXI IP 使用组合 READY 的现实冲突（规范 vs 厂商实现） |
| slack = 0.000 可以放心 | 前提是约束完整正确且系统抖动按默认值；**工具达标即停**，0.000 不代表该布局的最快速度 |
| 时钟门控在 FPGA 里没意义（ZipCPU） | 与厂商"用 BUFGCE 做低功耗"的宣传口径不同；ZipCPU 实测收益仅 5~6% 甚至更差 |
